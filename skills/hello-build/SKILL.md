# 实现纪律

## 此刻该怎么想

实现应延续项目约定，改动范围以完成用户需求为准。

- 有已确认的方案就按方案实施；没有方案但需求清楚，就直接做。多种做法都满足需求时自行选择并说明重要取舍；只有尚未明确的决定会实质改变用户目标、公开接口或存量数据时才提问，先完成不依赖该决定的工作。
- 新代码要像项目原有代码：先读一两处同类实现，再沿用既有技术栈、目录组织、命名与错误处理方式。想引入新依赖或新模式时，先确认现有能力确实做不到，并把理由讲给用户。
- 实现前按实际影响和风险确定验证范围：优先复用现有测试或复现步骤；缺少关键行为覆盖时补充，不为低影响改动编写只复述实现的测试。
- 按影响范围安排验证：复杂改动分步检查，简单改动完成后检查；没有新变更、失败或未解决风险时，不重复运行已通过的检查。
- 贴着任务改：改动范围以完成需求为准。顺手发现的无关问题（别处的 bug、可重构的旧代码）记下来交付时告知，不趁机扩大战场。
- 连带改动改完整：改了接口就改完所有调用方，改了行为就同步改相关注释与文档，不把仓库留在一半新一半旧的中间态。
- 实现中发现方案某处行不通时，选最贴近方案意图的替代做法，并把偏差与原因明确讲出来，不默默偏离。

## 什么才算完成

- 验收标准逐条走通，而不是“代码写完了”。
- 完成相关验证；需要系统性自检时使用 hello-qa，不因实现完成而自动追加完整检查。
- 交付说明改动与关键验证输出；有方案偏差或未完成事项时说明原因，不填充无关的“不做清单”。

## 交付前自问

- 这些代码放进项目里，像不像和原有代码出自同一人之手？
- 与方案或需求的每一处偏差都说明了吗？
- 验证输出附了吗？
