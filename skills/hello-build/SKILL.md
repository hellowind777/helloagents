# 实现纪律

## 此刻该怎么想

实现的目标是让改动无缝融进项目，而不是在项目里留下自己的风格印记。

- 动手前先锁定目标形态：有已确认的方案就按方案做，方案里的“不做清单”同样是边界；没有方案但需求清楚，就直接做。发现存在多种合理做法，或改动会波及公开接口、持久化数据时，先按 hello-plan 技能对齐再动手，不赌一个方向写完再说。
- 新代码要像项目原有代码：先读一两处同类实现，再沿用既有技术栈、目录组织、命名与错误处理方式。想引入新依赖或新模式时，先确认现有能力确实做不到，并把理由讲给用户。
- 先想好怎么验证再写实现：能补一个最小测试就先补上，写代码时就有靶子；补不了的，至少想清楚完成后跑什么命令、看什么结果。
- 小步前进：每完成一个可独立验证的片段，就跑一次最快的检查（类型检查、相关单测），不攒到最后一把梭。
- 贴着任务改：改动范围以完成需求为准。顺手发现的无关问题（别处的 bug、可重构的旧代码）记下来交付时告知，不趁机扩大战场。
- 连带改动改完整：改了接口就改完所有调用方，改了行为就同步改相关注释与文档，不把仓库留在一半新一半旧的中间态。
- 实现中发现方案某处行不通时，选最贴近方案意图的替代做法，并把偏差与原因明确讲出来，不默默偏离。

## 什么才算完成

- 验收标准逐条走通，而不是“代码写完了”。
- 按 hello-qa 技能自检，把验证命令的关键输出附在交付里。
- 交付时说清：改了哪些文件、为什么这样改、与方案的偏差在哪、明确没做什么。

## 交付前自问

- 这些代码放进项目里，像不像和原有代码出自同一人之手？
- 与方案或需求的每一处偏差都说明了吗？
- 验证输出附了吗？
