# 需求探索

## 此刻该怎么想

PRD 的质量取决于讨论的质量，文档只是讨论结果的沉淀。目标是把模糊的想法变成一串可以判断对错的决定，而不是把想法翻译成文档腔。

- 沿维度推进：目标用户与痛点、核心场景、功能边界、非功能要求（性能、安全、合规等）、验收标准；产品形态需要时再引入新维度（多角色带出权限，涉及收费带出计费）。每个维度谈到有明确结论，或用户明确说跳过。
- 一次聚焦一个维度，由你先出牌：基于已有信息给出推测和推荐，让用户修正，不让用户对着空白想。用户的回答里冒出新信息时追下去，比按清单走完更重要。
- 挑战与记录同样重要：范围蔓延时就建议砍，两条需求互相矛盾就当场指出，“最痛的用户是谁”答不上来就停在这个问题上。顺从地记下一个有问题的需求，是这项工作里最贵的失败。
- 边界要问到“不做什么”：明确排除的场景、用户、功能写进文档，和“做什么”同等重要。
- 允许回头：后面的讨论推翻了前面的结论，就回去改结论，不为表面一致护短。

## 好 PRD 的标准

- 激活的维度才展开，跳过的维度不出现在文档里，不为完整性填表。
- 清楚记录需求、背景、理由与验收条件，保留理解决定所需的上下文，不照录讨论过程或为压缩篇幅省略依据。
- 验收标准具体到可以直接据此验收，不是愿景的复述。
- 一个没参与讨论的人拿到它就能开工，不需要再来问“你们当时是怎么想的”。

## 落盘与后续

- 项目里有 .helloagents/ 时写入 .helloagents/plans/；尚无项目目录时按用户指定的位置输出。
- 确认后要实现的，按 hello-plan 或 hello-build 技能继续；PRD 记录“要什么”，实现方案记录“怎么做”，不混在一份文档里。

## 交付前自问

- 每个激活的维度是有结论，还是只有讨论痕迹？
- 有没有为了显得完整而保留的小节或套话？
- “不做什么”写清楚了吗？
