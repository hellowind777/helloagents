# 复盘

## 触发条件

10→只有满足下列任一条件时才执行复盘，不满足则跳过——普通顺畅的任务通常不触发，不需要为了「做过复盘」而硬写。

1. 走了弯路才发现真相：最初方案行不通，换方案才成功。
2. 用户纠正了你的方向：你的初始判断是错的，用户的纠正包含了值得记住的信息。
3. 多轮试错才通过：至少两次不同的尝试后才找到正确做法。
4. 发现了从代码里看不出来的坑：隐藏依赖、环境怪癖、历史原因、非直觉的配置。

## 此刻该怎么想

20→- 复盘的产出是给未来会话的信息差：下次遇到同类任务时，提前知道它能少走弯路的东西才值得写。
- 记结论与理由，不记过程：未来的读者需要「方案甲在这个项目行不通，因为乙，改用丙」，不需要这次尝试的流水账。
- 抽象到可复用的层次：绑定具体代码行的经验会随代码失效，抽象成「这个项目里改甲类东西要先看乙」才能复用；但「要仔细测试」这类放之四海皆准的话不值得占一行。

## 知识分层与落点

| 类型 | 落点 | 示例 |
|---|---|---|
| 项目事实（技术栈、架构、关键约束） | context.md | 「这个项目使用 pnpm 而非 npm，因为需要 workspace 协议」 |
30→| 做法约定（非显而易见的编码规则） | guidelines.md | 「这个项目的报错信息统一用中文，返回值用英文键名」 |
| 模块级经验（特定模块的坑或模式） | notes/{模块}.md | 「认证模块的 token 刷新逻辑不走标准 OAuth，原因见……」 |
| 方案级决策 | 对应 plans/ 目录 | 在方案的决策记录中补充 |

## 写法与查重

- 写之前查重：已有的不重写；与旧条目矛盾时更新旧条目，不留两种说法并存；发现已失效的旧经验顺手删掉——过期知识比没有知识更误导人。
- 一条经验两三行封顶，写长了说明还没提炼完。
- 每条经验都说得出未来哪类任务会用到它，说不出场景就不写。
40→
## 交付前自问

- 这条经验下次什么场景会用到？说不出场景就不写。
- 不了解本次对话的读者，单独读这条能懂吗？
- 有没有为了「做过复盘」而凑数的条目？有就删。
