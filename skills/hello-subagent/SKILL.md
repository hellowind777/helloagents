# 子代理协作

## 此刻该怎么想

派出子代理时：

- 在宿主允许委派时，把边界清晰、可独立验证且有并行收益的任务交给子代理；任务很小或需要频繁往返时自己完成。根代理和子代理适用同一判断。
- 委派说明包含目标、范围、必要上下文、完成判据与验证方式。按宿主实际的上下文继承方式补充信息，不假定子代理一定能或不能看到历史。
- 按交付证据判断结果，检查关键改动与集成影响；同一代码状态下已有的有效检查可以复用，不重复整个子任务。
- 明确文件或模块所有权，避免同时写入同一文件；告知子代理不要回退他人的改动。合并结果后由派出方负责整体一致性。

作为子代理时：

- 你的读者是上级代理，不是最终用户。产出以信息密度为先：结论、关键证据、改动点、遗留风险；寒暄、过程叙述、成果渲染都是噪音。
- 边界即契约：只做委派的事。执行中发现范围外的问题，报告它，不顺手扩大战线。
- 任务定义有歧义又无法追问时，选最合理的解释执行，返回时说明按哪种理解做的——让上级有机会纠正，而不是沉默地赌一个方向。
- 阻塞时返回有用的失败：试过什么、卡在哪、缺什么才能继续，让上级能直接决策，而不是一句“做不了”。

## 好协作的标准

- 委派语单独可执行，不依赖“你懂的”的隐含上下文。
- 交回的结果可直接验证或直接使用，上级不需要重做一遍。
- 出了问题能定位责任段：是定义不清、执行有误，还是汇合失当。

## 交付前自问

- 这段委派语交给一个不知情的人，能做对吗？
- 子代理交回的东西，我验证过还是只看了汇报？
- 作为子代理，我的返回里有没有为最终用户准备的表演成分？
