# 安全视角

## 此刻该怎么想

- 先画信任边界：哪些数据来自边界之外——用户输入、第三方接口、上传文件、地址参数、请求头。它们在被验证之前一律不可信，包括“自己前端传来的”。
- 按风险分配注意力：认证、授权、支付、执行外部内容的地方值得反复推敲；内部工具的展示逻辑不必同等待遇。安全上的平均用力等于重点失守。
- 想攻击者会怎么用，而不只是用户会怎么用：把资源编号换成别人的会怎样？重放这个请求会怎样？把文件名换成带 ../ 的路径会怎样？
- 注入的通用解法是把数据与指令分开：SQL 用参数化查询，拼接命令行不掺用户输入，输出到页面时做编码。“过滤掉危险字符”的黑名单思路默认可被绕过。
- 授权要检查所有权，不只检查角色：登录了不等于有权访问这一条资源。每个按编号取资源的入口都要问一句“这条属于当前用户吗”。

## 敏感信息的流向

- 对密码、令牌、身份信息追踪全程：传输是否加密、存储是否哈希或加密、日志与错误信息里是否泄漏、返回给前端的字段是否超出需要。
- 错误信息对用户讲结果，对日志讲细节：堆栈、SQL、内部路径只进日志，不出接口。
- 密码只存单向哈希（bcrypt 或 argon2）；令牌设过期时间；密钥的去处是环境变量或密钥服务，并确认相关文件不进版本库。

## 好防护的标准

- 每个信任边界上都有验证，验证用白名单描述“什么是合法”，而不是枚举“什么是危险”。
- 权限判断在服务端、靠近资源访问处；绕过前端绕不过检查。
- 失败即关闭：验证不通过、权限判断出异常时拒绝请求，而不是放行。

## 交付前自问

- 这次改动的信任边界在哪？每个边界上有验证吗？
- 换一个用户的资源编号重放请求，会拿到别人的数据吗？
- 敏感信息会出现在日志、错误响应或前端多余字段里吗？
