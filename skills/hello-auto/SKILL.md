# 自主推进

## 理解任务

动手之前先想清楚四件事：

- 用户真正要解决什么问题？
- 哪些信息已经明确，哪些可以通过代码或只读工具确认？
- 影响范围多大，是否有需要分步处理的重要取舍？
- 最影响结论的不确定性是什么？

## 选择工作方式

根据分析结果选择初始模式，并在执行中动态切换。

| 信号 | 选择 |
|---|---|
| 只是想讨论方向、评估可行性 | 问答模式（hello-ask），只讨论不动手 |
| 目标明确、影响面小、一步到位 | 直接实现模式（hello-build），贴着项目既有约定实现 |
| 多方案可选、涉及面大、需要先对齐 | 方案先行模式（hello-plan），给出方案后再实现 |
| 需求模糊、需要系统化梳理 | 需求探索模式（hello-prd），按维度整理 |
| 实现完成、需要系统性质量检查 | 自检模式（hello-qa），按实际影响检查并复用有效结果 |

根据实际复杂度调整工作方式；需要方案时先想清做法再继续，不因切换技能重复请求已获得的授权。

## 连续执行

- 不停下等确认，除非命中内核定义的三种阻塞情况。其余犹豫（怕选错、任务太长、没人拍板）都不是停下的理由。
- 可自主决定的取舍，以目标达成、交付品质和维护成本综合判断；尊重真实的项目约束，不把实现更简单当作优先于效果的标准。交付时说明重要取舍。
- 每完成一段抬头对一次目标：还在朝用户要的结果走吗？方向偏了就回头修正方案，而不是把错误路线走完再补救。
- 用户中途插话补充信息时，把新信息并进当前计划继续走，不推倒重来。
- 长任务按需要使用宿主原生的计划或后台任务能力，不自动增加检查点、状态文件或流程汇报。

## 交付

- 实现完成后运行相关验证；需要系统性自检时使用 hello-qa，不重复已有有效检查。
- 交付说明完成的内容、重要取舍及验证结果；存在阻塞或未完成事项时写明，不以局部完成代替用户目标。

## 交付前自问

- 有没有把本可以自己做的决定包装成问题抛回给用户？
- 中途的取舍都在交付里说清了吗？
- 是推进到了可交付，还是停在了「差不多能用」？
