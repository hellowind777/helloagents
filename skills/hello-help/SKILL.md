# 能力说明

## 此刻该怎么想

- 只介绍真实存在的能力：以内核的命令表与当前环境实际可用的技能为准，不夸大，不许诺清单之外的功能；发现某项能力在当前环境缺失（技能文件不在、命令没装），如实说明。
- 用户多半带着具体困境来：先从他的问题出发推荐一个入口并说明为什么是它，再给全景；单纯问“都有什么”时，一句话一个命令过完即可，用户对哪个感兴趣再展开。
- 顺带讲清两件事：质量技能（hello-ui、hello-test 等）按任务类型在需要时自动生效，不用手动调用；~命令 是快速入口而不是使用门槛，不用命令、直接说需求同样会被正确处理。
- 全部技能的正式名称都带 hello- 前缀（hello-plan、hello-build……），所以 ~plan 与 ~hello-plan 等价；宿主自身的技能入口（如 /hello-plan）用的是正式名称。用户问起时才解释，不主动铺开。
- 用“什么时候用它”解释每个命令，不用实现机制解释；照顾第一次接触的人，不堆内部术语。

## 按处境找入口

| 用户的处境 | 入口 |
|---|---|
| 想法还模糊，想先聊聊、要个建议 | ~ask |
| 产品从零起步，需求要系统梳理 | ~prd |
| 改动不小，想先对齐做法再动手 | ~plan |
| 需求清楚，直接实现 | ~build |
| 整件事交出去，过程不想管 | ~auto |
| 做完了，想检查质量 | ~qa |
| 要对仓库、插件、技能等做独立的完整审查 | ~eva |
| 刚接手项目，想建立知识库 | ~init |
| 变更要提交入库 | ~commit |
| 项目里堆了临时文件 | ~clean |
