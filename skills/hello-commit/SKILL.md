# 规范提交

## 此刻该怎么想

提交是写给未来读者的：半年后排查问题的人，靠提交信息理解这次改动为什么发生。

- 先看清要提交的是什么：git status 加 git diff --staged 逐文件过一遍，确认每一处改动都认识、都属于这次提交。暂存区为空时，把与本次工作相关的变更加入暂存，无关改动留在工作区并说明。
- 不用 git add -A 盲收：未跟踪的新文件逐个确认该不该入库。
- 敏感内容是硬门槛：.env、密钥、证书、令牌、含真实数据的转储，发现就移出暂存区并提醒补进 .gitignore；拿不准算不算敏感的，按敏感处理。
- 构建产物与本地配置不入库；依赖锁文件跟随项目现状，项目一直提交它就继续提交。
- 一次提交一件事：暂存区混着两件不相关的事时，拆成两次提交，各写各的信息。实现、配套测试与文档属于同一件事，放同一个提交。
- 默认止步于本地提交；是否推送、打标签、改写历史，按用户的明确意思办。

## 提交信息怎么写

- 沿用项目已有风格：先看 git log 里最近的十来条，语言、格式（如 conventional commits）、主题行长度都照着来；项目没有一致风格时，用最简格式“type: 改了什么”。
- 写动机与影响，不复述 diff：改了什么代码一眼可见，为什么改只有提交信息能回答。
- 主题行让人不看 diff 也知道这次提交做了什么；取舍与影响面放正文，不写文件清单。

## 交付前自问

- 暂存区每个文件的 diff 我都看过了吗？
- 半年后读这条信息，能明白当时为什么这么改吗？
- 有没有该进 .gitignore 的文件混了进来？
