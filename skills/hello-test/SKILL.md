# 测试策略

## 此刻该怎么想

- 测试的价值在于它失败时告诉你什么。写每个测试前先答：它能抓住哪类真实缺陷？答案是“没有”的测试是负资产——不提供保护，只增加维护成本。
- 测行为不测实现：通过公共接口验证外部可观察的结果。重命名一个内部函数就变红的测试，锁定的是实现形状，不是正确性。
- 根据缺陷所在层级和实际风险选择测试：业务逻辑与算法通常用单元测试，模块协作用集成测试，关键用户流程用端到端测试；不为层级齐全重复覆盖同一行为，也不预设测试数量。
- 修缺陷先建立复现步骤或失败测试，再用同一手段确认修复；已有有效复现测试时直接复用，不重复新增。
- 根据已有证据选择尚未覆盖的关键行为，包括成功路径、边界与失败路径；不假定正常流程已经验证，也不机械遍历与改动无关的边界。

## 脆弱与失败的处置

- 断言具体值，不满足于“不为空、没抛错”；一个测试验证一个行为，失败时能直接指向原因。
- 消灭不确定来源：时间、随机数、执行顺序、外部服务。替身只用于外部依赖，不用于被测代码本身；不得不伪造内部协作者时，先怀疑测试切入点选错了。
- 失败的测试只有两种正当出路：修代码，或证明测试的期望本身错了再改测试。为了变绿而放宽断言、加重试、跳过用例，等于拆掉报警器。
- 检查测试能否区分正确与错误行为。只有断言有效性仍存疑时，才在隔离环境中用错误输入或受控变更验证，不要求每个测试都故意改坏实现。

## 好测试的标准

- 名字读出来是一条行为规格，失败信息不看代码也能懂。
- 能承受内部重构：改实现不改行为时保持全绿。
- 独立可重复：单跑、乱序跑、连跑多次结果一致。

## 交付前自问

- 每个测试失败时，我能立刻知道坏在哪吗？
- 本次是否增加了只复述实现、重复已有覆盖或只为覆盖率数字存在的测试？有就调整；不据此删除用途尚未查清的既有测试。
- 边界和失败路径测了吗，还是只测了顺路的成功场景？
