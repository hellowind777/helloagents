# 排障思路

## 此刻该怎么想

- 第一步是完整读原始报错——不截断、不转述、不凭标题猜。栈的最上层几帧、报错里的具体值（路径、类型、行号）往往已经写明了答案。
- 没有稳定复现就没有调试，只有碰运气。先建立能证明“问题出现、问题消失”的最小手段：一个失败测试、一段脚本、一条命令都行。没有它，改完了也不知道是修好了还是没触发。
- 复现之后才轮到假设：列两三个按可能性排序的可疑点，每个都可证伪——“如果原因是 X，在 Y 处会看到 Z”。一次只改一个变量，验证一个假设。
- 范围大就二分：注释掉一半、回退到已知正常的提交（git bisect）、在数据流中点设观测点，每次把嫌疑砍半，比逐行盯看快得多。
- 区分症状与根因：抛错的位置常常不是制造问题的位置。沿数据流向上游追，找到第一个不对的值是在哪产生的。在抛错处加判空、包一层捕获让报错消失，多半是把病往深处赶。
- 最近改了什么是最高价值的线索：提交历史、依赖升级、配置变更。昨天还好今天坏的问题，答案几乎总在这中间。

## 卡住时

- 同一方向修了三次还不行，说明假设本身错了：停下来重读报错、扩大阅读范围、质疑“我确信不会错”的那部分——被验证过的确信才算确信。
- 临时日志和实验代码在收尾时清干净；确要保留的观测点，要能说出保留的理由。

## 好修复的标准

- 能讲清因果链：从触发条件到错误现象的每一环。“改了这里就好了但不知道为什么”不算修完。
- 修复后用同一复现手段确认问题消失，并尽量沉淀为回归测试。
- 修的是根因产生处，不是症状暴露处。

## 交付前自问

- 我能用一句话讲清这个缺陷的因果链吗？
- 修复前它稳定复现、修复后同一手段确认消失了吗？
- 同类问题在别处还有吗？顺手查过了吗？
