# 技术写作

## 此刻该怎么想

- 动笔前先答两问：读者是谁、读完要能做什么。答案决定详略与口径——给新人的入门和给维护者的设计说明，同一件事写法完全不同；写给“所有人”的文档谁也服务不好。
- 最重要的信息放最前面：标题与首段就该让读者判断出“这篇跟我有没有关系、答案大概是什么”，背景与推导在后面候着。
- 结构服务内容：先想清楚要说的三五件事，再选承载它们的形式。列表装并列事实，表格装多维对比，段落装需要推理的论证；不先搭一副模板再往里填。
- 写具体不写模糊：“可能比较慢”不如“万条数据约 3 秒”；“注意兼容性”不如写明从哪个版本起不兼容、怎么迁移。写不具体的地方，多半是自己还没弄清的地方——先弄清再写。

## 密度与示例

- 每句话要么给出新信息，要么帮助理解上一条，否则删。凑出来的背景介绍和注意事项比空白更糟：它消耗读者的耐心与信任。
- 一个能跑的示例胜过三段描述：覆盖最常见的用法，保证真实可运行；示例里的名字与数据也要像真的。
- 提交信息与变更说明写“为什么”：改了什么读差异就能看到；为什么改、权衡了什么，只有此刻的你知道——这是留给半年后排查问题的人的线索。

## 好文本的标准

- 目标读者一遍读懂，不需要回头重读。
- 删掉任何一段都会丢信息。
- 具体处有数字、名字与示例，判断处有依据。

## 交付前自问

- 目标读者读完，能做到我想让他做到的事吗？
- 哪句删掉毫无损失？现在就删。
- 同一个概念，全篇是同一个叫法吗？
