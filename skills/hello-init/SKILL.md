# 初始化项目知识库

## 此刻该怎么想

知识库的价值在于密度：后来者读十分钟，省下自己摸索两小时。达不到这个标准的内容不如不写。

- 先在项目根目录执行 helloagents init：它同步用户级运行副本，写入或更新 AGENTS.md 的受管标记块（块外内容不动），补充 .helloagents/ 下缺失的 context.md、guidelines.md 模板文件，并建立 plans/ 与 archive/ 目录。verify.yaml 由后续调查填入真实命令；DESIGN.md 与 notes/ 仅有实际内容时按需创建。命令不可用时如实说明原因，不手写一份仿制的内核冒充。
- 然后读取 README、构建与持续集成配置、入口文件和相关模块；只有这些信息不足时再扩大范围。目的不是读完代码，而是分辨哪些信息代码自己会说、哪些不会。
- context.md 只收从代码看不出来的事实：项目目标与用户、如何运行与验证、外部约束（接口、数据格式、合规）、非直觉决策的原因。目录树、依赖清单、函数签名这类代码自己会说的不写，写了只会过期。
- 浏览中找到的真实验证命令（lint、test、build）写进 .helloagents/verify.yaml，同时也在 context.md 的运行与验证一节注明——verify.yaml 是机器可读的版本，context.md 是给人看的说明。
- guidelines.md 只记录与通用惯例不同的项目约定及其原因，与默认做法相同的不写。
- 不编造：浏览之后仍不确定的事（部署方式、某条约束的来历），要么问用户，要么不写；不填一句「看起来合理」的猜测。知识库里错误的事实比空白危害大得多。
- AGENTS.md 设计上随仓库分发给整个团队，默认入库；.helloagents/ 是否入库遵循项目现状与用户意愿。
- 重复执行时，知识库模板文件只补缺失、不覆盖已有内容；AGENTS.md 受管块和用户级运行副本仍会同步更新。核对既有知识库是否过期，只更新已核实的事实。

## 完成的样子

- AGENTS.md 与 .helloagents/ 就位，context.md 里每句话都核实过。
- 交付时说明：写入了什么、哪些信息没找到、建议用户补充什么。

## 交付前自问

- context.md 里有没有从代码就能看出来的内容？有就删。
- 有没有拿不准却写得像事实的句子？
- 用户补两句话就能填上的空白，我问了吗？
