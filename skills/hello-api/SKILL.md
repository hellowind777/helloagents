# 接口设计

## 此刻该怎么想

- 站在调用方一侧设计：先写出理想的调用代码或请求示例，再倒推接口形状。调用方写起来别扭的接口，实现得再干净也是坏接口。
- 一致性高于局部最优：命名风格、分页方式、时间格式、错误结构，跟全项目现有惯例保持一致。一个更漂亮但不同款的新端点，是给每个调用方增加一条特例记忆。
- 错误是接口的正式组成部分，与成功响应同等设计：稳定的错误码供程序分支，说人话的错误信息供人读，该带的细节（哪个字段、违反什么约束）带上。调用方拿到错误后应该知道下一步做什么，而不是只知道失败了。
- 状态码说真话：语义准确的 4xx 与 5xx 是调用方的第一层分支依据；一律返回 200 再在包里放错误字段，等于逼每个调用方自建一套判断。
- 发布过的接口就是承诺：新增字段或可选参数不自动等于兼容。确认旧请求仍有效、旧客户端能接受新增响应字段、默认语义不变；新增必填请求字段、改语义、删字段、改类型按破坏性变更处理，要么版本化，要么新旧并行过渡后再下线。用旧消费者或其契约测试验证，不只测试新客户端。先确认接口是否真的“发布过”——没有外部调用方的内部接口不必背这个包袱。
- 每个列表接口都要问规模长大后怎么办：分页、过滤、排序在第一版就定型，事后补分页本身就是一次破坏性变更。

## 防御与限度

- 入参在边界处完整校验：类型、范围、必填，尽早失败并指明是哪个参数、错在哪。
- 对外暴露的写操作考虑幂等：网络会重试、调用方会重发，同一请求执行两次不该产生两笔。
- 外部调用应有与调用类型相符的超时、取消或生命周期策略；公开端点在存在容量、滥用或资源耗尽风险时设计限流，并明确错误语义和适用边界。新增这些行为前先检查现有契约和业务要求。

## 好接口的标准

- 只看接口定义与示例就能正确调用，不需要读实现。
- 同类操作长得同款：见过一个端点，就能猜对第二个。
- 错误响应可编程分支，也可直接向用户转述。

## 交付前自问

- 我以调用方的身份把调用代码写一遍，顺手吗？
- 每种失败情况，调用方拿到的信息够决定下一步吗？
- 这次改动会破坏已有调用方吗？确认过，还是假设的？
