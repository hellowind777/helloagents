# 文本与指令可执行性检查

> 加载时机：被审对象**是**或**包含**下列任一类内容时加载，并对命中的那部分（可仅为仓库中的子集）执行本检查——指令、规则、提示词、agent / 系统提示、技能（含 SKILL.md 与技能说明）、政策 / 规范 / 操作手册、面向执行者的流程说明，以及其他将由人或 AI 按文执行的文本。
>
> 本文件不是固定审查面清单，也不是文体评分表。目标只有一个：找出会让执行者（人或 AI）**理解错、触发错、执行错或无法兼容后续表述**的真实问题。

## 适用范围

- **整包是文本**：例如单独的提示词、规则文件、技能目录、政策文档——对全文适用。
- **更大对象中的一部分**：例如代码仓库里的 `SKILL.md`、`.cursorrules`、agent 提示、贡献规范、运维手册——只对识别出的指令/规则/提示类节点深入，不要对业务代码注释做全面的文风检查。
- **调查中新发现**：覆盖对象图里后来才出现的同类文件或片段，补载本文件并补查，不必重开整次审查。

## 检查要点

1. **可唯一理解、可执行**：关键指令是否只有一种合理读法？有无隐喻、黑话、行话、过度学术或口号式空话挡住动作？有无因赘述或过度精简导致条件、范围、例外说不清？
2. **用词与语种**：在面向人的中文指令语境下，是否自然、清晰、准确、合理、统一、专业？是否存在非必要的中英文混杂（协议名、API、品牌、必须保留的技术专名除外）？
3. **门控与匹配方式**：行为触发、允许/拒绝、路由、模式切换是否过度依赖脆弱的关键词或字面硬编码，以致换一种同义表述或后续版本措辞就失效？必要硬编码（安全拒绝列表、协议常量、法定原文、稳定 API 名等）应保留并在结论中区分“必要”与“过度”。在能安全提升通用性与兼容性时，是否更宜用语义条件而非关键词开关？
4. **结构与标点是否伤义**：句中硬断行、中文引号方向错误、列表层级混乱、条件与例外缠在一起——仅当已造成或很可能造成歧义、截断或误执行时才报告；纯审美标点不升为关键问题。
5. **编码与路径文字**：若该类文本配套脚本或说明涉及读写文件、中文路径或中文内容，是否要求（或实现上保证）以 UTF-8 处理？默认编码假设是否会在真实环境出错？

## 严重度与呈现

- 默认多为**中**或**低**；仅当导致错误触发、错误拒绝、安全绕过、关键流程不可执行、或跨版本大面积失效时升为**高**（可利用的注入/外传/越权仍按安全定义，可至阻断）。
- 必须满足发现质量门：有位置依据、说清期望与实际、写明对谁的影响；不得把个人文风偏好写成缺陷。
- 同一根因（例如全库统一用关键词门控）合并为一条，下列出多处表现。

## 与其它按需检查的关系

- 对象同时是 AI 工件（技能 / MCP / 插件 / agent 提示）时：本文件与 `references/agentic-security.md` **一并**加载；安全问题优先按安全定义定级，表述/门控问题按本文件。
- 本文件约束的是**被审文本**；审查报告自身的文风见 `references/report-template.md`，不要混用。
