# 验证设计：证伪能力、证据强度与通过类结论的标准

> 加载时机：主诉求包含验证时；或整理“已验证通过”“承诺验证总表”这类通过类结论时；或拿不准某次观察够不够格判“通过”时。
>
> 本文件不是测试用例设计手册，也不是验证项清单。它只解决一件事：**判断一次观察是否真的验证了某条承诺**。观察怎么做仍由你现场决定。

## 核心判据：这次观察本可能失败吗

判定“通过”之前，问一句：**如果这条承诺其实不成立，我刚才这次观察会不会呈现不同的结果？**

- 答案是“会”——观察具备证伪能力，判定成立。
- 答案是“不会”——观察不构成验证。它只证明了对象能运行，没证明承诺成立。
- 答案是“不知道”——按“不会”处理，先想清楚这次观察的结果由什么决定。

这一问替代了一切用例设计规则。跑一次正常路径就判“输入校验完备”通过，之所以不合格，不是因为用例太少，而是因为**不管校验写没写，那次运行的结果都一样**。

## 承诺类型与最低证伪要求

不是要你逐类照做，而是提醒：这几类承诺天然带失败路径，只观察成功路径必然不具备证伪能力。

| 承诺形态 | 只看这个不算验证 | 至少要看到 |
|---|---|---|
| 处理坏输入 / 校验完备 | 正常输入跑通 | 至少一次坏输入，且行为符合声称的处理方式 |
| 缺省配置安全 / 有合理默认值 | 完整配置下能启动 | 移除该配置项后的实际行为 |
| 错误恢复 / 失败降级 | 正常流程走完 | 人为制造失败后的实际走向 |
| 并发安全 / 幂等 | 单线程单次调用成功 | 并发或重复调用下的实际结果；做不到就记“无法验证” |
| 权限限制 / 拒绝越权 | 授权路径可用 | 一次应当被拒绝的调用，确认它真的被拒绝 |
| 边界与容量 | 典型规模下正常 | 至少一次边界值或超限输入 |
| 一致性（文档与实现、多处声明之间） | 读了其中一处 | 两处并列比对，逐项对上 |
| 存在性 / 完整性（如“列出了全部 14 项能力”） | 印象上齐全 | 逐项点数并列出对应关系 |

最后两类不需要运行，但仍具备证伪能力——比对和点数在承诺不成立时会给出不同结果。**证伪能力不等于必须动态执行。**

## 证据强度阶梯

同一条承诺，能用上层手段就不要停在下层。下层不是非法，但必须在结论里如实标明强度。

1. **可观察行为**：真实运行、真实调用、构造输入触发，直接看到结果。最强。
2. **交叉比对**：两个及以上独立来源逐项对上（文档与实现、多处声明之间、声明与调用链）。
3. **调用链追溯**：静态追出从入口到该行为的完整路径，确认可达且无覆盖它的分支。
4. **静态推理**：只读代码，靠逻辑推断。**单独使用时不足以判“通过”**，只能支撑“未发现反例”，须与上层手段配合或标为疑似。
5. **文档自述**：对象自己声称如此。这是被验证的对象，不是证据。

判断降级时机：能上不上是偷懒；条件不具备而下降是诚实——后者必须写明缺什么条件。

## “无法验证”的正确用法

“无法验证”不是失败，也不是通过，是一个独立且合法的结论。它出现在三种情形：

- **缺外部条件**：需要真实凭证、生产环境、特定硬件、第三方服务。写明缺什么、补齐后怎么验。
- **缺证伪手段**：想得到承诺可能怎样不成立，但在当前环境造不出那个条件（典型如并发竞态）。写明想验什么、为什么造不出。
- **承诺本身不合格**：表述模糊到两个人会得出不同判定。写明模糊在哪，这本身通常是一条“中”级发现。

**不要为了让表格好看把“无法验证”写成“通过”。** 一份诚实标注三条“无法验证”的报告，比一份全绿但经不起追问的报告有用得多。

## 通过类结论的对照样例

**不合格（不得这样写）**：

| 检查项 | 结果 |
|---|---|
| 配置加载 | ✅ 通过 |
| 错误处理完善 | ✅ 已检查，实现完整 |
| 安全性 | ✅ 无明显问题 |

为什么不合格：第一条没写观察方式；第二条“已检查”是过程陈述不是证据，“实现完整”是印象；第三条“无明显问题”既没说查了什么，也没说怎么查的——三条都不具备证伪能力，读者无法自行判断可信度。

**合格（按此标准撰写）**：

| 检查项 | 结果 |
|---|---|
| 配置加载 — 缺省环境变量 | ✅ 移除 `API_BASE` 后启动，回退到 `config.py:88` 的内网默认值并打印告警，与 `docs/config.md:12` 声明一致 |
| 输入校验 — `parse_range()` | ✅ 构造 `"5-2"`、`""`、超长串三类坏输入，均按 `utils/parse.py:40` 抛 `ValueError` 并被入口捕获 |
| 越权拒绝 | ✅ 以只读令牌调用写接口，返回 403 且未产生写入（已核对数据库行数不变） |
| 文档与实现一致性 | ✅ README 列出的 14 项能力逐项在源码中定位到实现，无悬空项、无未声明的公开入口 |
| 并发安全 — 计数器累加 | ⚠️ 无法验证：本环境无法稳定复现竞态；`counter.py:31` 的读改写序列未加锁，属疑似问题 #4 |

每条都写明了观察方式，且承诺不成立时结果会不同。最后一条示范了诚实降级：它没有假装通过。

## 与其它文件的关系

- 验证过程中发现的**实际缺陷**按 `references/finding-quality.md` 的质量门与严重度定级，写入问题清单；本文件只管“通过”一侧的判定标准。
- “这条承诺验证通过”与“这一维评估为强”是两类结论，不要互相替代：验证通过说明它没骗人，不说明它做得好。评估侧的标准见 `references/evaluation-judgment.md`。
- 报告中这些结论的呈现位置与表格写法见 `references/report-template.md`。
